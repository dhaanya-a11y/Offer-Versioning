# Display Only Offer — Versioning

For a **Display Only Offer**, versioning ensures that changes to customer-facing content and configuration are made in a controlled and auditable manner. Once the offer is live, changes are made through a new version and follow the applicable approval process.

## 1. Offer Type & Structural Fields

| Change | Decision | Reason |
|---|---|---|
| Offer Type | **Not Allowed** | Different offer types use different processing engines. Changing the Offer Type would effectively create a different offer. |
| Eligibility Level | **Not Allowed** | Enrollment records are built based on this configuration. |
| Issuer | **Not Allowed** | Changing the issuer creates a cross-issuer configuration risk. |
| Program Type | **Not Allowed** | Changes the underlying processing pipeline. |

## 2. Basic Details & Offer Scope

| Change | Decision | Reason |
|---|---|---|
| Offer Name | **Allowed — On V2 Approval** | Internal text. No customer impact. |
| Offer Description | **Allowed — On V2 Approval** | Internal text. |
| Offer Duration — Extend | **Allowed — On V2 Approval** | Offer remains visible for a longer period. No negative impact. |
| Offer Duration — Shorten | **Allowed — On V2 Approval with Warning** | The system warns that the offer end date is being shortened and that customers currently viewing the offer may have noted the original end date. The checker reviews the change. |
| Program — Add New | **Allowed — On V2 Approval** | More customers can see the offer. No existing customers are affected. |
| Program — Remove Existing | **Not Allowed** | Customers on this program may be actively viewing the offer. Removing the program cuts their access. A new offer without this program is the correct path. |

## 3. Set-Up Offer — User Base

| Change | Decision | Reason |
|---|---|---|
| Static ↔ Dynamic | **Not Allowed** | Static and Dynamic use different enrollment engines and data structures. |
| Opt-In ↔ Smart Tag Attachment | **Not Allowed** | Different enrollment mechanisms. |
| Static — Add Members | **Allowed — On V2 Approval** | Expands the audience that can see the offer. |
| Static — Remove Members | **Not Allowed** | Removes access for customers who may currently be viewing the offer. |
| Dynamic — Add Smart Tag | **Allowed — On V2 Approval** | Allows additional segments to see the offer. |
| Dynamic — Remove Smart Tag | **Not Allowed** | Removes visibility for customers associated with the Smart Tag. |
| Eligibility Criteria — Add | **Allowed — On V2 Approval** | Allows the bank to refine or expand the target audience. |

## 4. Home Display

| Change | Decision | Reason |
|---|---|---|
| Labels | **Allowed — On V2 Approval** | Visual only. |
| Display Title | **Allowed — On V2 Approval** | Controls the offer title shown to customers. |
| Display Description | **Allowed — On V2 Approval** | Controls the offer summary shown to customers. |
| Display Order | **Allowed — On V2 Approval** | Controls the position of the offer in the offer list. |
| Display Color | **Allowed — On V2 Approval** | Visual branding only. |
| Offer / Merchant Logo | **Allowed — On V2 Approval** | Visual branding only. |
| Background Illustration | **Allowed — On V2 Approval** | Visual branding only. |

## 5. Offer Details Page

| Change | Decision | Reason |
|---|---|---|
| T&C / Rich Text Content | **Allowed — On V2 Approval** | Any change to live T&C content must go through V2. The system provides a diff view and retains the previous version for audit and dispute resolution. |
| CTA Button Text | **Allowed — On V2 Approval** | Non-financial but customer-facing content. |
| Redirection Link | **Allowed — On V2 Approval** | Customer-facing link. Checker review is required because an incorrect link can direct customers to the wrong page. |
| Advanced Settings | **Allowed — On V2 Approval** | Display configuration. |

## How Display Only Versioning Works — Step by Step

### Step 1 — Publish the Initial Offer

The bank configures and publishes the Display Only Offer. The published configuration becomes **V1**, which is the version currently visible to customers.

Once V1 is live, changes cannot be made directly to the live version.

### Step 2 — Identify the Required Update

When the bank needs to modify the offer, it first identifies the fields that need to be changed.

For example:

- Update the offer description
- Change the display title
- Extend the offer duration
- Add a new program
- Update the T&C content

### Step 3 — Create a New Version

The bank creates **V2** from the currently live version.

V2 starts with the existing V1 configuration, while **V1 continues to remain active**. This allows the bank to prepare and review changes without affecting the live offer.

### Step 4 — Configure the Changes

The bank updates the required fields in V2.

Fields that are structurally locked, such as **Offer Type, Eligibility Level, Issuer, Program Type, and Static ↔ Dynamic**, cannot be modified.

Allowed fields can be updated according to the versioning rules.

### Step 5 — Review the Version Changes

The system provides a comparison between the existing version and the new version.

The bank can review the differences between **V1 and V2** before submitting the changes for approval.

For changes such as T&C or rich-text content, the previous version is retained so that the change can be reviewed later.

### Step 6 — Submit the New Version

After reviewing the changes, the bank submits V2 for approval.

The updated version then moves through the applicable **maker-checker approval process**.

### Step 7 — Checker Validates the Changes

The checker reviews the proposed changes before they are applied to the live offer.

The checker can either:

- Approve the new version
- Send it back with comments for further changes

### Step 8 — Approved Version Becomes Live

Once V2 is approved, it becomes the active version of the Display Only Offer.

Customers then see the updated configuration and customer-facing content.

### Step 9 — Version History Is Maintained

The previous version remains available as part of the version history.

This provides an audit trail of changes made to the offer and allows the bank to track how the offer configuration and content evolved across versions.
