### Scenario — Reducing the Reward Rate

A bank has launched a Transactional Offer that rewards customers with **5 reward points per transaction**. After monitoring the campaign, the bank decides to reduce the reward rate to **3 points** to control the cost of the offer.

Without versioning, the bank would need to duplicate the offer and configure the new offer again. The new offer would then need to be managed separately from the existing offer.

With versioning, the bank can create **V2** and update the reward value from **5 points to 3 points**. Once V2 is approved, the new reward value applies to subsequent transactions while the existing offer configuration and customer enrollments are retained.

**Why Versioning Helps**

Versioning allows the bank to make configuration changes through a controlled new version without recreating the offer.

---

## The Solution — Live Offer Versioning

Live Offer Versioning allows the bank to create a new version of an existing live offer.

- **V1** remains active while **V2** is being configured.
- The bank can make changes to the fields that are allowed for versioning.
- Once V2 is approved, it replaces V1.
- Existing customer enrollments are retained.
- The bank does not need to duplicate and reconfigure the entire offer.

The key question is:

> **Which fields can change in V2, and which cannot?**

This document defines the versioning rules for **Transactional Offers**.

---

# Transactional Offer

A **Transactional Offer** is an offer where eligibility and the reward outcome are evaluated based on a transaction.

For a Transactional Offer, versioning supports changes to specific **offer, eligibility, transaction, reward, usage-limit, narration, and display configurations**.

Configurations that represent the underlying offer structure or restricted processing behaviour cannot be modified through versioning.

# Stage 4.1 — User Base

The **User Base** defines **who gets the offer and how they get enrolled**.

This is the most complex section because the customer enrollment model cannot be changed freely after the offer is live.

## Static and Dynamic User Base

Static Base and Dynamic Config use fundamentally different enrollment mechanisms.

- **Static** stores a fixed list of account IDs.
- **Dynamic** stores Smart Tag rules that evaluate in real time.

The underlying data schemas are different. Switching between these configurations invalidates existing enrollment records.

For Transaction Offers, creating a new offer has zero customer impact because there are no counters to lose. Therefore, changing the enrollment model should be handled through a new offer.

### Why Static → Dynamic Is Not Allowed

1. **Different systems** — Static uses a fixed list, while Dynamic uses a rule engine. They cannot be swapped mid-offer.
2. **No accountability** — After switching, it becomes unclear who is enrolled and why.
3. **Not a version** — Changing the audience model represents a new offer rather than a versioning change.

# Stage 4.2 — Transaction Eligibility

**Transaction Eligibility** defines which transactions qualify for the offer.

It includes:

- MCC
- MID
- TID
- POS Entry Mode
- Transaction Value
- Transaction Type
- Sovereignty Indicator
- Transaction Code
- Date for Processing

## Scenario — Missed MCC

A bank launches a Transactional Offer and later realizes that **MCC 5912 (Drug Stores)** was missed. **10,000 customers** are already enrolled.

Without versioning, the bank would need to:

- Duplicate the entire offer.
- Reconfigure the offer, requiring **2–4 hours of operations time**.
- Lose the **10,000 customer enrollments** on the new offer.
- Create a coverage gap where qualifying Drug Store transactions earn nothing.

With versioning, the bank can add **MCC 5912** in V2. Once V2 is approved, the next qualifying Drug Store transaction earns the configured reward.

No duplication or re-enrollment is required.

---

## Removing Transaction Attributes

If the bank removes **MCC 5411 (Grocery)**, the next grocery transaction simply does not earn.

For Transactional Offers, there is **no counter or accumulated progress**. Each transaction is evaluated independently.

The customer was never told that MCC 5411 is included; they see **"earn on grocery"** on the app.

# Stage 4.5 — Posting

**Posting** is the reward delivery infrastructure. It controls when and how earned rewards reach the customer's account.

## Posting Enable / Disable

The **Posting Enable / Disable** toggle is **Not Allowed** in V2.

Posting is configured as **ON or OFF at offer creation**.

Turning Posting OFF mid-offer means rewards are calculated but never delivered, creating an unclear state for both the bank and the customer.

Turning Posting ON mid-offer raises questions about whether previously calculated rewards should be backfilled.

Therefore, the Posting toggle cannot be changed through versioning.

# How Transactional Offer Versioning Works

### Step 1 — Edit a Live Offer

The bank clicks **Edit** on a live offer from the **Manage Offers** page.

### Step 2 — Create V2

The system creates **V2 as an exact clone of V1**.

V1 remains fully active while V2 is being configured.

All enrolled customers continue earning under the V1 rules.

### Step 3 — Edit V2

The bank makes the required changes in V2.

The **diff view** displays:

- **Green** — Added
- **Red** — Removed

Only fields allowed by the versioning rules can be edited.

Locked fields are greyed out, with the reason for the restriction displayed.

### Step 4 — Review V2 Summary

The system automatically generates the **V2 Summary**.

The summary includes:

- All Same Cycle changes.
- For Transactional Offers, there are no cycles, so all changes apply on approval as a **V1.1 minor version**.
- A warning if a field is both added and removed within the same version.

### Step 5 — Apply Changes

Before submitting V2, the bank can choose how the changes are applied.

#### Option 1 — Apply All Changes Together

All changes are applied together when V2 is approved.

**Recommended for Transactional Offers.**

#### Option 2 — Split Changes

Some changes can be applied immediately while others are applied in the next cycle.

This option is relevant to **Milestone Offers**.

### Step 6 — Maker-Checker Approval

Once V2 completes the approval process:

- V2 goes live.
- V1 is archived.
- A full audit trail is maintained.
